title: 项目
notes:
  - 做任何需要用心做的项目之前都要先讨论，最好能多轮讨论直至完全对齐、收敛，再形成一份总设计文档，最终构建阶段按照这份文档来构建（当然，如果整个项目很庞大，需要分模块，那当然可以根据唯一权威文档来做文档的分块，这样可以增加并行度、提高构建效率）。
  - 构建大型项目的时候需要权衡是否使用框架，以及使用什么框架。比如我本人很喜欢用GSD Core + Claude Code，最终的效果的确很出色，但是耗时很长、token烧的肉疼。
  - 数据驱动的项目，先处理数据（搜集、爬、清洗、划分），再做规划，规划也需要花大功夫，不要直接稀里糊涂规划以后就上手构建实施了。
  - 大型项目、多Agents并行执行、构建的，需要合理的git管理制度。最重要的就是conflict和工作区的交叉影响，目前最好的方法是隔离的、独立的git worktree，在各自的worktree里做的时候，合并回主分支时不用太担心交叉影响的问题，有conflict就resolve就行了，不会出现工作区污染的错误（虽然现在的AI已经可以识别这种污染了，通过diff等技巧来判别工作区干净，但是有一套完善的版本管理机制还是可以免去很多不必要的麻烦的）。
  - '个人很喜欢的一套适合多Agents并发的workflow: 计划文档定义任务与依赖 → 波次（Wave）作为调度单位把任务批量派给并行子代理（各在自己的 git worktree）→ 每个任务完成时回写状态文件 → 本地看板服务跨 worktree 实时聚合 → 里程碑末尾按 Gate 判据验收 → 解锁下一里程碑。把一个大目标切成多块小的里程碑对于高质量构建在目前的(2026.10.10)工程实践上是非常有帮助的，目前的Agents还无法handle一个太大的目标并且高质量构建出来。分块还是必要的。'
  - |-
    几个常常拿出来当作工作流且经常维护的文档：
    current.md 当前状态+交接 (这个不作为硬依据，作为软链接，方便下一个Agent更好抓住下一步是什么)
    complete.md 完成清单 (这个无关紧要，主要是看着里程碑被做完比较有成就感，实感)
    issues.md 问题台账（这个非常非常重要，在构建过程中遇到的问题不是每次都能即使被修复的，即使修复了后续如果再碰到也无从考究，所以需要一个记录文档，记录问题详情、根因诊断、问题状态。这一份文档能少走很多弯路）
    timeline.md 里程碑事件，比如Gate通过与否（这个不太重要，还是提供实打实的情绪价值用的）
    decisions/YYYYMMDD-XXX.md 执行期技术决策，含问题、上下文、诊断、方案选择等等。（这个比较重要，跟问题台账的原因差不多，留痕为重）
